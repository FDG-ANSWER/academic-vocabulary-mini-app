# Sprint Retrospective

## What Went Well

- The recovery sprint focused on a small, usable product instead of starting unnecessary features.
- The required learning and quiz functions were identified as the highest priorities.
- The work was structured into GitHub Issues and a Project Board.
- The application uses simple technologies and has no backend or personal-data collection.
- Immediate answer feedback and retry support improved the educational value of the quiz.

## What Caused Problems

- The original requirements were not converted into a complete, testable backlog early enough.
- The initial quiz implementation did not meet the six-question requirement and needed correction.
- Some documentation files were created before their content was completed.
- Testing evidence and Board status need to be updated continuously, rather than left until the end.

## What I Learned

- Every assessment requirement should be converted into a user story and acceptance criterion before implementation starts.
- A Definition of Done makes it clearer when a task can truthfully move to Done.
- Testing early identifies gaps, such as the missing fifth and sixth quiz questions, before final submission.
- Small, meaningful commits and accurate development logs provide stronger evidence of genuine Agile progress.
- Accessibility and privacy should be considered from the beginning, not treated as final checks.

## Improvements for Future Work

- Review the requirements checklist at sprint planning, during development and before Sprint Review.
- Create a test case when each user story is added to the sprint.
- Limit work in progress by completing and testing one feature before beginning another.
- Update the Project Board immediately when a task changes status.
- Schedule regular time for documentation and reflection during the sprint.

## Collaboration and Communication in a Professional Agile Project

In a professional Agile team, progress, blockers, risks and requirement changes should be made visible through daily communication, a shared backlog and a Project Board. Changes should be discussed with the Product Owner or stakeholder, assessed against the Sprint Goal, and recorded as backlog updates rather than introduced informally. Team members should raise blockers early, document important decisions, review completed work with stakeholders and use the retrospective to improve the next sprint.
